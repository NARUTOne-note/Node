# 消息队列（MQ）

> MQ = Message Queue，消息队列。简单说就是一个**"消息中转站"**：发送方不用直接找接收方，把消息丢进队列，接收方按自己的节奏来取。

类比：就像**邮局**——你写信丢进邮筒（生产消息），邮局（Broker）负责存着、转交，收信人（消费者）什么时候来取都行。发信人不用等收信人在线。

## 为什么要用 MQ

- **流量削峰**：10 万请求涌进来，数据库顶不住。先全塞进 MQ，再按数据库能承受的速率（比如每次取 1000）慢慢消费，慢一点但不崩。
- **应用解耦**：A 不再直接调用 B，而是发消息给 MQ。B 挂了不影响 A，B 恢复后继续从 MQ 取消息接着干。
- **异步通信**：发消息后立刻返回，不等处理完。比如发短信、写日志，用户不用干等。

## 三大主流对比

| 维度 | RabbitMQ | Kafka | Pulsar | RocketMQ |
|------|----------|-------|--------|----------|
| 出身 | Erlang 写的消息代理（AMQP） | LinkedIn 出的分布式日志流 | Yahoo 出的分布式消息/流 | 阿里出的分布式消息中间件 |
| 存储模型 | 队列存内存/磁盘，取走即删 | 顺序日志（append），按留存期 | 计算与存储分离，消息存 BookKeeper | CommitLog 顺序写盘 + 主从复制 |
| 吞吐量 | 万~十万级/秒 | 百万级/秒 | 百万级/秒 | 十万级/秒 |
| 延迟 | 微秒级（最低） | 毫秒级 | 毫秒级 | 毫秒级 |
| 消息可靠 | 高（ACK、确认机制全） | 高（多副本 + 日志） | 高（多副本 + Quorum） | 高（同步刷盘 + 主从切换） |
| 顺序保证 | 队列内有序 | 分区内严格有序 | 分区内有序 | Queue 内有序 |
| 扩展难度 | 分片/镜像队列，较复杂 | 加 Broker + 分区迁移 | 加 Broker 即可（存储独立扩展） | 加 Broker 即可，Queue 自动分散 |
| 多租户 | 弱 | 一般 | 原生强支持（namespace/tenant） | 一般（Topic/消费组隔离） |
| 业务功能 | 路由规则最丰富 | 偏日志流，业务功能少 | 队列 + 流双模型 | 事务/延迟/顺序消息开箱即用 |
| 适合场景 | 业务路由、任务分发、复杂路由规则 | 日志/埋点/流式数据、高吞吐消费 | 既要高吞吐又要灵活路由、多租户、存算分离 | 电商/金融等强业务场景、事务/延迟/顺序消息 |

## 怎么选

- **要复杂的路由规则**（广播、按 key 分发、模糊匹配）、**延迟低到极致** → **RabbitMQ**
- **海量数据吞吐**、日志收集、事件溯源、流计算 → **Kafka**
- **既要大流量又要存算分离易扩展**、多租户、同时要队列模型 + 流模型 → **Pulsar**
- **电商/金融等业务场景**、要事务消息、延迟消息、顺序消息开箱即用 → **RocketMQ**

## 小结

- MQ 的本质：**削峰、解耦、异步**，三件事。
- 没有"最好"的 MQ，只有"最合适场景"的 MQ：要路由选 Rabbit，要吞吐选 Kafka，要兼顾扩展与灵活选 Pulsar，要业务功能选 Rocket。
- 什么时候不该用：单机小工具、调用方与被调方必须同步拿结果、消息量极小且无削峰需求——直接函数调用更简单。
